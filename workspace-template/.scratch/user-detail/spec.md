# 用户详情查看功能 Spec

**Status:** ready-for-agent

## Problem Statement

现有产品已经具备用户列表、User 模型和用户查询接口，但用户无法从列表进入一个稳定、可读的详情视图。普通用户需要确认自己的基础账号信息，管理员需要处理任意用户的问题；如果缺少明确的权限边界、字段范围和异常反馈，详情能力容易造成越权访问、敏感信息泄露或不一致的用户体验。

## Solution

在现有用户列表中提供详情入口，点击某一用户行后进入独立详情页，并以该用户的稳定唯一 ID 调用现有查询接口。普通用户只能查看自己的详情，管理员可以查看任意用户。页面只读展示基础资料、账号状态、创建时间和更新时间，并提供加载中、无权限、不存在、字段为空及服务异常状态。

首期复用现有 User 模型、查询接口、登录态和角色体系，不建设新的用户数据源。权限必须由服务端在每次详情请求中校验，前端入口控制仅用于改善体验，不能替代鉴权。

## User Stories

1. As an 普通用户, I want 从用户列表进入自己的详情页, so that 我可以核对账号基础信息。
2. As an 普通用户, I want 只看到自己有权查看的信息, so that 其他用户的资料不会被越权访问。
3. As an 管理员, I want 从用户列表进入任意用户的详情页, so that 我可以处理用户支持和账号问题。
4. As an 用户, I want 在详情页看到用户 ID、姓名或昵称、头像、邮箱、手机号, so that 我可以识别并核对该账号。
5. As an 用户, I want 在详情页看到账号状态, so that 我可以判断账号当前是否可用。
6. As an 用户, I want 在详情页看到创建时间和更新时间, so that 我可以了解账号信息的时间背景。
7. As an 用户, I want 空字段以统一方式呈现, so that 我不会把缺失数据误认为页面故障。
8. As an 用户, I want 在详情加载期间看到明确反馈, so that 我知道系统正在处理请求。
9. As an 无权限访问者, I want 看到明确且不泄露数据的拒绝提示, so that 我知道为何不能查看该详情。
10. As an 用户, I want 在目标用户不存在时看到明确提示, so that 我不会继续等待或误判为网络问题。
11. As an 用户, I want 在服务失败时可以重试或返回列表, so that 我可以恢复当前操作。
12. As an 用户, I want 从详情返回后保留原列表上下文, so that 我可以继续先前的浏览工作。
13. As an 安全负责人, I want 敏感字段沿用现有脱敏规则, so that 新页面不会扩大个人信息暴露面。
14. As an 管理员, I want 权限由服务端执行, so that 篡改页面 URL 或用户 ID 不能绕过权限。
15. As an 产品维护者, I want 详情使用独立页面和现有数据契约, so that 后续可以扩展而不重复建设用户模型。

## Implementation Decisions

- 使用现有用户列表作为唯一首期入口；点击用户行时携带稳定、不可变的用户 ID，不能仅凭姓名或昵称查询。
- 详情采用独立页面，并沿用宿主产品现有导航、视觉组件和路由约定。
- 详情为只读视图，不提供编辑、启停、删除、密码重置或导出操作。
- 复用现有 User 模型和用户详情查询接口，不新增第二套用户数据源或冗余详情模型。
- 首期基础资料包括用户 ID、姓名或昵称、头像、邮箱和手机号；字段以现有模型为准，值为 `null`、空字符串或缺失时显示“暂无”。
- 展示现有账号状态枚举及其既有文案，前端不得自行推断状态。
- 展示创建时间和更新时间，格式统一为 `YYYY-MM-DD HH:mm`，时区沿用宿主产品默认时区。
- 普通用户仅能读取与当前登录身份相同的用户 ID；管理员可以读取任意用户 ID。管理员身份复用现有登录态和角色体系判定。
- 每次详情请求均由服务端鉴权。无权限时返回 403 或宿主系统等价错误，且响应不得包含目标用户字段。
- 目标用户不存在时返回 404 或宿主系统等价错误；其他失败使用通用服务错误，不展示半份或上一次用户的数据。
- 敏感字段沿用现有脱敏和可见性规则；若宿主系统尚无明确规则，本功能不得扩大明文暴露范围。
- 返回用户列表时，保留宿主列表已有的筛选、分页和滚动位置能力。
- 不要求数据库或 schema 变更；若现有接口缺少已存在于 User 模型中的约定字段，只允许扩展现有接口契约，不另建数据源。

## Testing Decisions

- 采用最高可用行为缝进行验证：以当前登录身份和目标用户 ID 发起详情访问，断言最终页面状态及服务端响应，不测试内部函数调用顺序。
- 主路径覆盖普通用户从列表进入本人详情，并验证约定字段、状态和时间展示。
- 权限路径覆盖管理员查看任意用户、普通用户直接构造他人 ID、未登录访问；重点断言越权响应不含用户数据。
- 状态路径覆盖加载中、空字段、404、通用服务错误、重试和返回列表上下文。
- 接口测试验证现有详情契约及 403/404 语义；页面或端到端测试验证列表入口、独立页面、反馈文案和返回行为。
- 优先复用宿主项目现有的鉴权接口测试与页面导航测试模式。当前产品工作区未包含宿主业务代码，开发开始前需由实现者定位具体测试工具和既有范例。

## Out of Scope

- 新建用户列表、搜索、筛选、分页或排序能力。
- 编辑用户资料、启用或禁用账号、删除用户、重置密码或导出数据。
- 最近活动、业务统计、权限配置、操作日志或审计历史。
- 新建用户数据模型、替换存储系统或建设新的角色权限体系。
- 为管理员新增独立白名单或可配置 RBAC 管理界面。

## Further Notes

- 本 Spec 假设宿主系统已经具备用户列表、User 模型、用户详情查询接口、登录态、管理员角色和字段脱敏规则。
- 当前工作区是产品文档模板，不包含宿主业务代码；接口名称、路由名称和具体字段标识应在开发接入时依据宿主系统确认，但不得改变本 Spec 的外部行为和权限边界。
- 若宿主系统缺少管理员角色、详情接口或脱敏规则，应先报告依赖缺口并调整实现计划，不得由详情页面临时发明替代机制。
